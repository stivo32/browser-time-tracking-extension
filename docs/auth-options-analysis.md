# Анализ вариантов аутентификации для Browser Time Tracking Extension

## Контекст проекта

- **Frontend**: Browser Extension (Chrome/Edge/Firefox)
- **Backend**: FastAPI (Python 3.12)
- **Требования**: Синхронизация между устройствами, облачное хранение
- **Приватность**: Локальное хранение для MVP, опциональная облачная синхронизация

## Варианты аутентификации (от простого к сложному)

### 1. HTTP Basic Authentication (самый простой)

#### Как работает:
```
Запрос содержит заголовок: Authorization: Basic base64(email:password)
```

#### Плюсы:
- ✅ Простота реализации
- ✅ Не требует дополнительных механизмов хранения токенов
- ✅ Нет состояния на сервере (stateless)

#### Минусы:
- ❌ Пароль передается при каждом запросе (риск перехвата)
- ❌ Нет механизма истечения токена без повторного входа
- ❌ Нет возможности отозвать доступ
- ❌ Низкая безопасность для долгоживущих сессий

#### Когда использовать:
- Только для внутренних API
- Демо/прототипы
- Не подходит для production

---

### 2. Session-based Authentication (традиционный подход)

#### Как работает:
```
1. POST /login → сервер создает сессию в БД/Redis
2. Возвращает session_id в cookie
3. Все запросы содержат cookie с session_id
4. Сервер проверяет сессию в БД/Redis
```

#### Плюсы:
- ✅ Возможность отозвать доступ (удалить сессию)
- ✅ Полный контроль на стороне сервера
- ✅ Безопасность (пароль не передается повторно)
- ✅ Можно хранить дополнительную информацию в сессии

#### Минусы:
- ❌ Требует хранение сессий (БД/Redis) - не stateless
- ❌ Масштабирование требует общей БД сессий или sticky sessions
- ❌ В браузерных расширениях работа с cookies может быть сложнее

#### Когда использовать:
- Когда нужен полный контроль над сессиями
- Когда нужна возможность мгновенного отзыва доступа
- При наличии общего хранилища сессий (Redis)

---

### 3. API Key Authentication (для сервисов)

#### Как работает:
```
1. Пользователь создает API ключ в настройках
2. Все запросы содержат заголовок: X-API-Key: <key>
3. Сервер проверяет ключ в БД
```

#### Плюсы:
- ✅ Простота для клиента
- ✅ Легко генерировать/отзывать ключи
- ✅ Можно ограничить права доступа для разных ключей

#### Минусы:
- ❌ Нет истечения срока действия (требует явного отзыва)
- ❌ Ключ должен храниться на клиенте (риск компрометации)
- ❌ Не подходит для интерактивных пользователей (лучше для машин)

#### Когда использовать:
- Для интеграций (API для внешних сервисов)
- Для автоматизации
- Не подходит для основного механизма аутентификации пользователей

---

### 4. JWT (JSON Web Tokens) - текущий план

#### Как работает:
```
1. POST /login → сервер создает JWT с данными пользователя
2. Возвращает токен клиенту
3. Клиент хранит токен и отправляет в заголовке: Authorization: Bearer <token>
4. Сервер проверяет подпись токена (без обращения к БД)
```

#### Плюсы:
- ✅ Stateless (не требует БД для проверки)
- ✅ Масштабируемость (любой сервер может проверить токен)
- ✅ Можно встроить метаданные (exp, user_id, permissions)
- ✅ Стандартизированный формат (RFC 7519)
- ✅ Хорошо работает с микросервисами

#### Минусы:
- ❌ Сложно отозвать токен до истечения (нужен blacklist или короткий срок)
- ❌ Размер токена больше чем session_id
- ❌ Требует безопасного хранения на клиенте
- ❌ Если ключ скомпрометирован, все токены недействительны

#### Варианты реализации:

##### 4.1 Простой JWT (без refresh токенов)
```python
# Структура:
{
  "user_id": "123",
  "email": "user@example.com",
  "exp": 1700000000  # истекает через 30 минут
}
```
- Короткий срок жизни (15-30 минут)
- При истечении - повторный вход

##### 4.2 JWT с Refresh токенами
```python
# Access Token (короткий):
{
  "user_id": "123",
  "type": "access",
  "exp": 1700000000  # 15-30 минут
}

# Refresh Token (долгий):
{
  "user_id": "123",
  "type": "refresh",
  "exp": 1700064000  # 7 дней
}
```
- Access token для API запросов
- Refresh token для обновления access token
- Refresh token можно хранить в БД для возможности отзыва

##### 4.3 JWT с Blacklist
```python
# При logout добавляем токен в blacklist (Redis/БД)
# Проверяем blacklist при каждой валидации токена
```
- Позволяет отзывать токены
- Частично теряется преимущество stateless (нужна БД для blacklist)

---

### 5. OAuth 2.0 (для внешних провайдеров)

#### Как работает:
```
1. Редирект на провайдера (Google/GitHub/etc)
2. Пользователь авторизуется
3. Провайдер возвращает authorization code
4. Обмен code на access token
5. Использование access token для API
```

#### Плюсы:
- ✅ Пользователь не создает новый аккаунт
- ✅ Не храним пароли пользователей
- ✅ Доверие к крупным провайдерам
- ✅ Меньше ответственности за безопасность паролей

#### Минусы:
- ❌ Зависимость от внешних сервисов
- ❌ Сложность реализации
- ❌ Требует OAuth приложение у каждого провайдера
- ❌ Может быть избыточно для MVP

#### Когда использовать:
- Как дополнительный способ входа (SSO)
- Для корпоративных пользователей
- Когда не хотим хранить пароли

---

### 6. OpenID Connect (OIDC) (расширение OAuth 2.0)

#### Как работает:
Аналогично OAuth 2.0, но с добавлением:
- ID токен (JWT с информацией о пользователе)
- Стандартизированный профиль пользователя
- Проверка подлинности (не только авторизация)

#### Плюсы:
- ✅ Все плюсы OAuth 2.0
- ✅ Стандартизированная информация о пользователе
- ✅ Встроенная проверка подлинности

#### Минусы:
- ✅ Еще сложнее чем OAuth 2.0
- ❌ Избыточно для простого приложения

---

### 7. Mutual TLS (mTLS) (самый сложный)

#### Как работает:
```
Клиент и сервер обмениваются сертификатами
Каждый запрос проверяет сертификат другой стороны
```

#### Плюсы:
- ✅ Максимальная безопасность
- ✅ Нет передачи паролей/токенов
- ✅ Защита от MITM атак

#### Минусы:
- ❌ Очень сложная настройка
- ❌ Управление сертификатами на клиенте
- ❌ Не подходит для браузерных расширений
- ❌ Избыточно для большинства случаев

#### Когда использовать:
- Для B2B интеграций с высокими требованиями безопасности
- Внутренние сервисы
- Не подходит для нашего проекта

## Альтернативы JWT для передачи токенов

### 1. PASETO (Platform-Agostic Security Tokens)

#### Отличия от JWT:
- ✅ Меньше вариантов атак (меньше поверхность атаки)
- ✅ Более безопасные алгоритмы по умолчанию
- ✅ Меньше реализаций = меньше багов
- ✅ Проще в использовании

#### Минусы:
- ❌ Меньше библиотек и поддержки
- ❌ Меньше распространенность

#### Пример:
```python
# PASETO использует локальный и публичный режимы
# v4.local - симметричное шифрование (HS256)
# v4.public - асимметричное (RS256)
```

---

### 2. Branca Tokens

#### Отличия от JWT:
- ✅ Проще (меньше опций)
- ✅ По умолчанию использует безопасные алгоритмы
- ✅ Меньше размер токена

#### Минусы:
- ❌ Еще меньше распространенность
- ❌ Меньше библиотек

---

### 3. Fernet (из библиотеки cryptography)

#### Отличия от JWT:
- ✅ Симметричное шифрование (всегда шифрует payload)
- ✅ Простота использования
- ✅ Не включает payload в токен (безопаснее)

#### Минусы:
- ❌ Только симметричное шифрование (нужен общий ключ)
- ❌ Не стандартизирован (как JWT)
- ❌ Не содержит метаданные (exp, iat) - нужно проверять отдельно

#### Пример:
```python
from cryptography.fernet import Fernet

key = Fernet.generate_key()
f = Fernet(key)
token = f.encrypt(b"user_id:123,exp:1700000000")
```

---

### 4. Opaque Tokens (случайные строки)

#### Отличия от JWT:
- ✅ Полный контроль (хранятся в БД)
- ✅ Можно мгновенно отозвать
- ✅ Нет информации в самом токене

#### Минусы:
- ❌ Требует БД для проверки (не stateless)
- ❌ Меньше масштабируемость

#### Пример:
```python
# Генерация:
token = secrets.token_urlsafe(32)  # Сохраняем в БД
# Проверка:
session = db.get_session_by_token(token)  # Запрос к БД
```

---

### 5. Signed Cookies (для веб)

#### Отличия от JWT:
- ✅ Автоматически отправляются браузером
- ✅ Защита от XSS (httponly flag)
- ✅ Защита от CSRF (same-site flag)

#### Минусы:
- ❌ Работает только с cookies (не для всех клиентов)
- ❌ Ограничения размера
- ❌ Может быть сложнее в браузерных расширениях

## Рекомендации для нашего проекта

### Вариант 1: Простой JWT (рекомендуется для MVP)

**Почему:**
- ✅ Простота реализации
- ✅ Stateless (масштабируемость)
- ✅ Достаточно для синхронизации данных
- ✅ Быстрая разработка

**Реализация:**
```python
# Access token на 30 минут
ACCESS_TOKEN_EXPIRE_MINUTES = 30

# При истечении - пользователь перелогинивается
# Для браузерного расширения это приемлемо (раз в день максимум)
```

**Недостатки:**
- Нет мгновенного отзыва (но для MVP это не критично)

---

### Вариант 2: JWT с Refresh токенами (для production)

**Почему:**
- ✅ Удобство для пользователя (не нужно часто логиниться)
- ✅ Возможность отозвать refresh token
- ✅ Безопасность (короткоживущие access токены)

**Реализация:**
```python
# Access token: 15 минут
# Refresh token: 7 дней (храним в БД с возможностью отзыва)

# При каждом запросе проверяем access token
# При истечении - обновляем через refresh token
# При logout - удаляем refresh token из БД
```

**Недостатки:**
- Чуть сложнее реализация
- Требует хранение refresh токенов в БД

---

### Вариант 3: PASETO (альтернатива JWT)

**Почему:**
- ✅ Более безопасен из коробки
- ✅ Проще использовать (меньше опций)
- ✅ Все еще stateless

**Реализация:**
```python
# Используем библиотеку python-paseto
from paseto import create_key, create_signed_token

key = create_key()
token = create_signed_token(key, user_id="123", exp=exp_time)
```

**Недостатки:**
- Меньше распространенность
- Меньше документации

---

### Вариант 4: Session-based (если нужен полный контроль)

**Почему:**
- ✅ Полный контроль над сессиями
- ✅ Мгновенный отзыв доступа
- ✅ Можно хранить дополнительную информацию

**Реализация:**
```python
# Храним сессии в SQLite (для начала)
# При каждом запросе проверяем сессию
# При logout - удаляем сессию
```

**Недостатки:**
- Требует БД для проверки
- Меньше масштабируемость (но для MVP это не проблема)

## Итоговые рекомендации

### Для MVP (Фаза 2):
**Вариант: Простой JWT**

**Причины:**
1. Быстрая реализация (6-8 часов)
2. Достаточно для синхронизации данных
3. Stateless - легко масштабировать
4. Стандартный подход - много примеров

**Компромиссы:**
- Нет мгновенного отзыва (но для MVP это приемлемо)
- Пользователь перелогинивается раз в 30 минут (редко)

---

### Для Production (после MVP):
**Вариант: JWT с Refresh токенами**

**Причины:**
1. Удобство для пользователя
2. Возможность отзыва доступа
3. Безопасность (короткоживущие access токены)
4. Можно добавить позже (обратная совместимость)

---

### Альтернатива (если хотим избежать JWT):
**Вариант: Session-based с SQLite**

**Причины:**
1. Простота реализации
2. Полный контроль
3. Для нашего масштаба (SQLite) - вполне достаточно
4. Можно легко отозвать доступ

## Хранение токенов в браузерном расширении

### Варианты хранения:

1. **chrome.storage.local** (рекомендуется)
   - ✅ Шифруется браузером
   - ✅ Доступно из background/content scripts
   - ✅ Не доступно через обычный JavaScript (безопаснее)

2. **localStorage**
   - ⚠️ Доступно через обычный JavaScript (риск XSS)
   - ⚠️ Не шифруется дополнительно

3. **Session Storage**
   - ❌ Очищается при закрытии браузера (не подходит)

### Рекомендация:
```javascript
// Сохранение:
await chrome.storage.local.set({
  accessToken: token,
  refreshToken: refreshToken  // если используем
});

// Получение:
const { accessToken } = await chrome.storage.local.get('accessToken');
```

## Вопросы для решения

1. **Нужен ли мгновенный отзыв доступа?**
   - Если да → JWT + Refresh или Session-based
   - Если нет → Простой JWT

2. **Как часто пользователь будет использовать расширение?**
   - Часто → JWT + Refresh (удобство)
   - Редко → Простой JWT (достаточно)

3. **Планируется ли масштабирование?**
   - Да → JWT (stateless)
   - Нет → Session-based (проще)

4. **Есть ли требования по безопасности?**
   - Высокие → JWT + Refresh с короткими access токенами
   - Средние → Простой JWT
